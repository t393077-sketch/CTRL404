1. Project Idea / What We're Building

SEENIL ("See everything. Leave nothing.") is a defense-grade, two-tier AIOps observability platform built for strict zero-trust enterprise and defense environments.

Traditional APMs ship raw traces, unparsed logs, and configuration dumps to the cloud—inevitably leaking API keys, database credentials, PII, and customer payloads. SEENIL guarantees zero egress data leakage by physically decoupling data collection from analysis: - Tier 1 (Local Lens Agent) sits inside the customer’s private VPC or on-prem perimeter. It captures raw infrastructure, network, and application telemetry, scrubs passwords and tokens using combined Shannon entropy and deterministic regex filters, computes local summaries, and verifies payloads against an uncompromising allow-list schema. Raw logs, secrets, and environment dumps never leave the local environment. - Tier 2 (Central SaaS Cloud) receives strictly sanitized metadata (metric values, UTC timestamps, pseudonymous source IDs, categorical severity, and concise alert context). It executes multi-tenant ingestion, enforces Row Level Security (RLS), calculates dynamic rolling Median Absolute Deviation (MAD) baselines, correlates cross-signal incidents, generates explainable root-cause paths, and orchestrates policy-approved autonomous remediation.

6. Security & Privacy Plan

  1. Shannon Entropy + Regex Redaction:
  2. Every raw log line is scanned against deterministic regex masks covering passwords, API keys (sk-..., Bearer tokens), JWTs, credit card numbers, IPv4/IPv6 addresses, and emails.
  3. Text chunks with high Shannon entropy ($H > 3.8\text{ bits/char}$) are flagged as potential unmasked cryptographic secrets and replaced with [REDACTED:HIGH_ENTROPY].
  4. Strict Pre-Egress Allow-Listing:
  5. Every event is validated against payload.schema.json with "additionalProperties": false. If an engineer or compromised process attempts to attach an unauthorized field (e.g. raw_query, user_password), the agent drops the packet locally and writes a security violation event.
  6. Pseudonymous Source IDs:
  7. Real hostnames and MAC addresses never leave the customer machine. The agent computes: $$\text{source_id} = \text{"node_"} + \text{HMAC-SHA256}(\text{site_secret}, \text{hostname})[:12]$$
  8. Cryptographic Egress Proof:
  9. The agent maintains an immutable local SQLite table recording: timestamp, metric, raw_input, redacted_payload, and payload_sha256.
  10. Judges can inspect this side-by-side: proving that the canary password existed in local raw memory but arrived in the SaaS cloud as [REDACTED:PASSWORD].
  11. Multi-Tenant Row-Level Security (RLS):
  12. Tenant identity is derived purely from the agent's authentication token on the server side—never trusted from the payload body. Database sessions set app.current_tenant_id = :tenant_id, guaranteeing cross-tenant data leaks are mathematically impossible at the database engine level.

7. AIOps / Anomaly Detection Logic

Static threshold alerting fails in dynamic production environments. SEENIL combines static safety limits with dynamic Median Absolute Deviation (MAD) statistical baselines: 1. Dynamic Rolling Baselines: - For every metric stream $(tenant, source, metric)$, the cloud engine maintains a rolling 60-sample window. - Unlike standard deviation (which is easily corrupted by historical spikes), MAD computes: $$\text{Median} = \tilde{X} = \text{median}(X)$$ $$\text{MAD} = \text{median}(|X_i - \tilde{X}|)$$ $$\text{Modified Z-Score } M_i = \frac{0.6745 \cdot (X_i - \tilde{X})}{\text{MAD}}$$ - Any telemetry event with $|M_i| > 3.0$ is flagged as a statistical anomaly with an assigned confidence score ($50\% - 99\%$). 2. Four Health States & State Machine: - States: Excellent, Good, Fair, Poor. - Every single health transition stores the explicit mathematical reason (e.g. system_cpu_percent value 92.4% breached Fair threshold > 80%). 3. Stale Data Auto-Downgrade: - If a source stops transmitting for $>30$ seconds, SEENIL automatically downgrades its health state to Fair or Poor rather than falsely displaying stale data as "healthy".

8. Alert Correlation & Autonomous Recommendations

  1. Multi-Signal Sliding Window Clustering:
  2. Isolated threshold alerts cause alert fatigue. SEENIL’s correlator clusters concurrent anomalies occurring across the infrastructure within a 60-second sliding time window into a single unified Incident.
  3. Example: A spike in failed_logins_rate + CPU saturation on auth-proxy + canary secret intercepted $\longrightarrow$ Clustered into Incident inc_sec_8901: "Brute-Force Auth Spike & Rogue Token Canary Detected".
  4. Explainable Root Cause Diagnostics:
  5. The diagnosis is synthesized purely from allow-listed metadata (preserving the zero-leak trust boundary). It delivers human-readable root-cause reasoning explaining why the incident occurred and which metric was the initial lead indicator.
  6. Simulated Autonomous Remediation Pipeline:
  7. Policy Check: Matches incident against pre-approved enterprise runbooks (e.g. POLICY-SEC-AUTONOMOUS-01).
  8. Operator Approval: 1-click execution from the AIOps War Room.
  9. Cryptographic Audit Log: Computes SHA-256 hash chaining: $$\text{Execution Hash} = \text{SHA-256}(\text{incident_id} + \text{policy} + \text{operator_id} + \text{UTC timestamp})$$
  10. Rollback Safety: Automatically creates a configuration snapshot ID (e.g. snap_a11d32) before applying simulated mitigation.

9. Failure Handling (Outages, Retries, Duplicates)

  1. Local Outbox Buffering:
  2. If network connectivity drops or SEENIL Cloud returns HTTP 5xx / connection timeout, the agent catches the failure and commits the signed event into a local SQLite FIFO queue (outbox.db).
  3. Exponential Backoff & Order Preservation:
  4. When connection is restored, a background worker flushes the outbox in strict chronological order using the original payload_id and original event_time_utc.
  5. Idempotent Delivery (Zero Duplicates):
  6. Every event has a unique UUID payload_id. The cloud database enforces a UNIQUE constraint on payload_id.
  7. If an event is retransmitted post-outage, SEENIL Cloud detects the collision, increments a duplicate counter in duplicate_metrics, and returns HTTP 200 OK without inserting a second row.
  8. Offline Silence Detection ($\le 60\text{s}$):
  9. Agents emit heartbeats every 10 seconds. Cloud runs an asynchronous monitor every 10 seconds: if now - last_heartbeat > 60s, the node is marked Offline with UTC timestamp and transition reason recorded.

12. Things We're Unsure About / Remaining Questions Addressed

1. Agent / Local Collector

  • Metrics Collected: CPU %, Memory %, Disk %, Socket RTT (ms), Packet Loss %, Failed Login Rate, Canary Interception flag.
  • Collection Method: Standard Python libraries (psutil for host metrics, socket handshake probes for RTT, sliding window file tailer for logs). Zero third-party cloud agents.
  • Frequency: Metrics collected every 5 seconds; heartbeats emitted every 10 seconds.
  • Raw Data Storage: Raw data is stored only in local embedded SQLite (agent_local.db) in WAL mode. Raw data never touches the network or cloud storage.

2. Privacy Pipeline

  • Raw Data Collected: OS process metrics, system resource gauges, auth log entries (/var/log/auth.log or local equivalent).
  • Secret Redaction: Combined Shannon entropy calculation ($H = -\sum p_i \log_2 p_i > 3.8\text{ bits/char}$) plus deterministic regex masks for passwords, tokens, API keys, emails, and IPs, replacing matches with [REDACTED:type].
  • Allow-Listing: Pre-egress validator checks the outgoing JSON against shared/payload.schema.json with "additionalProperties": false. Packets with unknown fields are dropped locally.
  • Pseudonymous Source IDs: Computed via $\text{HMAC-SHA256}(\text{site_secret}, \text{hostname})[:12]$, prefixed with node_. Real hostnames never leave the customer network.

3. Authentication & Security

  • Token Management: Unique Agent Tokens pre-seeded and provisioned per tenant (token_alpha_sec_98124). Stored locally in agent configuration.
  • HMAC Signing: For every request, the agent computes $\text{HMAC-SHA256}(\text{agent_token}, \text{raw_json_bytes})$ and transmits it in the X-Signature header alongside X-Agent-Token. The cloud recalculates the hash over the raw bytes before deserializing.
  • HTTPS/TLS: Localhost HTTP/REST for hackathon demonstration with identical header-signing mechanics; production uses TLS 1.3 endpoints.

4. AIOps

  • Anomaly Detection: Rolling Median Absolute Deviation (MAD) modified z-score ($|M_i| > 3.0$). Completely robust against historical outlier distortion.
  • Alert Correlation: Sliding 60-second time window grouping concurrent metric breaches across related infrastructure nodes into a single incident entity.
  • Recommendation Generation: Rule-based expert system mapping correlated anomaly signatures to pre-approved SOC policies with natural-language explainable reasoning paths based strictly on metadata.

5. Web UI

  • Frontend Stack: Next.js 14 (App Router), Tailwind CSS, Lucide React icons.
  • Pages & Panels: Fleet Command Center (/fleet), Egress Proof Panel (/egress-proof), Reliability & SLAs (/reliability), Access Console (/).
  • Live Updates: Dual-mode: WebSocket connection (/ws/live?tenant_id=...) for instant event pushes with a 3-second resilient polling fallback.

6. Reliability

  • Local Buffering: Embedded SQLite FIFO outbox table. If HTTP POST fails, event is written to outbox with status pending.
  • Retry Strategy: Background thread polls outbox every 3 seconds with exponential backoff on consecutive failures; replays in chronological order.
  • Duplicate Handling: Payload UUIDs are unique. Cloud database enforces unique constraints; duplicate payloads return HTTP 200 OK and increment duplicate counters without double-storing.
  • Offline Agent Handling: Background task checks heartbeat timestamps every 10s. If delta $> 60\text{s}$, status switches to offline and health downgrades to Poor with timestamp and reason logged.

7. Global Readiness

  • Regional Ingestion: Tenant metadata models support region tags (e.g. ap-south-1). Cloud database can partition data residency by regional ingest endpoints.
  • UTC & Timezones: All events require both event_time_utc (ISO 8601 UTC) and source_tz (e.g. Asia/Kolkata). Ingest latency is calculated against UTC received time.
  • Out-of-Order Events: All dashboard feeds and SQL queries enforce ORDER BY event_time_utc DESC rather than received_at, ensuring replayed backlogged events slots into their true historical position.
